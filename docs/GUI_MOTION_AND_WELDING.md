# GUI motion planning and welding workflow

## GUI structure

- **Motion Test**: a straight path from the current TCP and a circle normal
  to World X/Y/Z. `show planned path` controls the RViz markers.
- **Welding Test**: a TCP1-to-TCP2 linear base path and a sinusoidal weave
  generated from either the saved linear or circle base path.
- **TCP Teaching**: captures the current TCP together with the six measured
  joint angles. `Plan to initial position` makes a plan-only MoveGroup request
  to those angles and publishes it to RViz; it never executes that plan.
- **Planned Path**: read-only World-frame waypoint list, hidden by default,
  with `Delete All`.
- **Digital I/O**: hidden by default. DI0 is TOUCH. A rising DI0 on either
  control box immediately captures that arm's current World-frame TCP.
- **Pipeline Status**: shows only `WAITING`, `ERROR`, or `RESULT` state.

## Path mathematics

The straight motion is

```text
p(i) = p0 + d * i/(N-1) * axis,  i = 0..N-1
```

where `axis` is interpreted in World or rotated by the current TCP
quaternion for tool reference.

For a circle with center `c`, radius `r`, and selected normal axis, two
orthogonal in-plane vectors `u` and `v` are selected and

```text
p(theta) = c + r * (cos(theta) * u + sin(theta) * v)
theta_i = 2*pi*i/N
```

The optional closing point is a copy of point 0 and therefore is not counted
as a unique point.

The weave is not rectangular. The base seam is first resampled by arc length,
then a sinusoidal transverse offset is applied:

```text
p_weave(s) = p_base(s) + A * sin(2*pi*C*s) * transverse_axis(s)
```

`A` is one-side amplitude, `C` is weave cycles, and `s` runs from 0 to 1.
Tool-axis weave rotates the transverse vector by the interpolated TCP
orientation. Position between taught poses is linear; orientation uses
shortest-path normalized quaternion interpolation.

## Why motion can feel jerky

The weave generator itself is sinusoidal, not a rectangle or trapezoid. The
main discontinuity candidates are sparse Cartesian samples, abrupt direction
changes, IK switching between nearby joint solutions, or controller tracking.
The GUI exposes two settings that directly affect the generated trajectory:

- velocity scale: stretches time and scales velocity/acceleration;
- Cartesian interpolation step: MoveIt's maximum Cartesian sampling step
  (5 mm default; a smaller value generally produces denser IK samples).

Trajectory timing is generated by Time-Optimal Trajectory Generation and then
smoothed by Ruckig using the configured joint velocity, acceleration, and jerk
limits. Calling this a trapezoidal profile would be inaccurate. If motion is
still jerky, compare plans at 5, 2, and 1 mm while keeping velocity fixed, and
inspect the planned joint trajectory for joint-space jumps before execution.

## Recommended welding scenario integration

Keep H600 setpoints and manual ARC controls out of the path GUI. Add a separate
`WeldingScenario` action/state machine that consumes an already approved path:

```text
READY
  -> validate robot + H600 feedback + path
  -> approach TCP1 with ARC OFF
  -> gas pre-flow
  -> ARC ON and confirm welding feedback
  -> execute approved seam trajectory
  -> ARC OFF
  -> gas post-flow
  -> RESULT or safe ERROR shutdown
```

The path GUI should submit the approved path and scenario preset only. The
scenario node should own interlocks, timeouts, ARC output, cancellation, and
the guaranteed ARC-OFF cleanup path. This keeps motion testing usable without
exposing welding outputs and provides one auditable place for welding safety.

## ROS 2 flow

```text
joint_states + TF + system_state(DI0)
              |
              v
        weld_action_gui
          |        |
          |        +--> RViz markers / display_planned_path
          v
   CartesianPath action
          v
 MoveIt GetCartesianPath -> TOTG -> Ruckig
          v
 FollowJointTrajectory controller -> rbpodo_ros2 hardware -> robot
```

The GUI never talks to `rbpodo` directly. This reorganization does not modify
either `rbpodo` or `rbpodo_ros2`.
